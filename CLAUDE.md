# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Power Platform **Code App** ("Supply Hub" / internal order supply app) built as a
Vite + React + TypeScript SPA, embedded in a Power Apps player iframe and backed by
Dataverse tables. Bootstrapped from the standard Vite React template and wired up via
`@microsoft/power-apps` (runtime) and `@microsoft/power-apps-vite` (build plugin).

## Commands

```bash
npm run dev            # vite dev server at http://localhost:5173
npm run build          # tsc -b && vite build -> ./dist (buildPath in power.config.json)
npm run lint            # eslint .
npm run preview         # preview the production build
npm run test            # vitest run — always run before committing any change
npm run test:watch      # vitest in watch mode
npm run test:coverage   # vitest run --coverage (reporting only, no threshold gate yet)
```

A committed Husky `pre-commit` hook (`.husky/pre-commit`, installed via
`npm install --save-dev husky` + `npx husky init`, wired to run on `npm install` via the
`prepare` script in `package.json`) runs `npm test` automatically on every `git commit`
and blocks the commit if any test fails. Run the suite manually before committing anyway
so you catch a failure before the hook does.

Unit tests (Vitest + `@testing-library/react`) live under `src/__tests__/`, mirroring
`src/`'s structure with flattened leaf names (e.g. `BaseButton.test.tsx`). Config is in
`vitest.config.ts` (kept separate from `vite.config.ts` so the `powerApps()` build
plugin never runs during tests) and `tsconfig.vitest.json` (kept separate from
`tsconfig.app.json` so test files never enter the production build's type-check).
Coverage is not fully built out yet — see **`docs/testing-plan.md`** for what's covered,
what's next, and what's deliberately deferred (hooks/pages that call generated Dataverse
services); update that file as work progresses and remove this pointer once it's done.
Use the `create-power-app-react-tests` skill to add tests for a given file.

Playwright is present only as a devDependency for headless UI driving (see
`.claude/skills/run-raftestpowerapp/`), not for the unit test suite above.

To run/screenshot the app end-to-end (headless browser driving, dev-server lifecycle,
gotchas like `timeout` not existing on macOS), use the `run-raftestpowerapp` skill
rather than reinventing the sequence.

### Power Platform CLI

Dataverse/environment operations (auth, pushing the app, managing data sources, regenerating
the `src/generated/` client from schema changes) go through the **`pa`** CLI
(`@microsoft/power-apps-cli`), not `pac`. Key groups: `pa auth`, `pa app` (init/push/run/list,
plus `add`/`remove`/`refresh` for `data-source`/`dataverse-api`/`flow`), `pa connector`,
`pa connection`, `pa solution`. After adding/changing Dataverse columns in the maker portal,
re-run the relevant `pa app data-source`/`dataverse-api` refresh command so
`src/generated/models` and `services` pick up the new columns.

## Architecture

### Generated Dataverse client — never hand-edit

`src/generated/` (models + services, one pair per Dataverse table) and
`.power/schemas/` (raw table schemas + `appschemas/dataSourcesInfo.ts`) are autogenerated
by the `pa` tooling from the Dataverse schema and the `databaseReferences` in
`power.config.json`. Every generated file is stamped "Do not edit this file directly."
Treat schema/column changes as something to make in the maker portal (or via `pa`) and then
regenerate — never patch the generated TS by hand.

Each Dataverse table gets a `<Table>Service` static class (`create`/`update`/`delete`/`get`/
`getAll`/`getMetadata`, all returning `IOperationResult<T>` with `.success`/`.data`/`.error`)
and a `<Table>Model` namespace (a `*Base` type plus the full record type). `power.config.json`
maps friendly data-source names (`catalogueitems`, `internalorders`, `users`, `securityroles`)
to Dataverse logical/entity-set names — that's the source of truth for which tables exist.

### Dataverse OData quirks (read before touching record shapes)

- Lookup/optionset fields don't come back with a plain "name" — Dataverse returns the raw
  value plus a `@OData.Community.Display.V1.FormattedValue` annotation alongside it. Use
  `getFormattedValue(record, attribute)` in `src/types.ts` to read the display text.
- Owner-type lookups (e.g. `_ownerid_value`) are stripped from the generated TS models
  entirely even though Dataverse returns them at runtime — read them via
  `getRawValue(record, attribute)` instead of a direct/unsafe property access.

### Auth and authorization flow (`src/App.tsx` + `src/hooks/`)

1. `useCurrentUser` calls `getContext()` from `@microsoft/power-apps/app` to get the signed-in
   player identity (`fullName`, `userPrincipalName`, Azure AD `objectId`).
2. `useSecurityContext` resolves that identity to a Dataverse `systemuserid` (first by AAD
   object id via `SystemusersService`, falling back to email/UPN match — the AAD object id and
   the Dataverse systemuserid are different GUIDs, hence the lookup), then loads Dataverse
   security roles via `RolesService` and derives `isOrderAdmin` / `isOrderUser` / `hasAccess`
   from role names (`"Order Admin"`, `"Order User"`).
3. `App.tsx` gates rendering on loading/error/`hasAccess`, then gates individual routes
   (`/all-orders`, `/reports`) behind `ProtectedRoute` using `isOrderAdmin`.

This means any new admin-only feature should key off `isOrderAdmin` from
`useSecurityContext`, not a fresh AAD/role lookup.

### Player iframe constraint

The Power Apps player embeds this app in an iframe with a fixed `src`, so reloading the
player wipes the URL hash/path. `App.tsx` persists the last route to `sessionStorage`
(`supplyhub:lastPath`, origin-scoped, survives the iframe being torn down/recreated) and
`RootRedirect` restores it on `/`. Keep this in mind before relying on URL state alone.

### UI structure

Route components live in `src/pages/` (`CatalogPage`, `MyOrdersPage`, `AllOrdersPage`,
`ReportsPage`), each paired with a CSS module (`*.module.css`); shared cross-page styles are
in `src/styles/shared.module.css`. Components used by only one page live alongside it (e.g.
`src/pages/CatalogPage/components/`); components used by two or more places live in
`src/components/shared/` (e.g. `Spinner`, `Modal`, `Pagination`, and the chart primitives in
`src/components/shared/charts/` — `BarChart`, `DonutChart`, `LineChart`, `TopItemsList`, shared
`colors.ts`). App-shell chrome (`Header`, `Sidebar`) lives in `src/components/layout/`; route
guards (`ProtectedRoute`) live in `src/components/guards/`. `src/components/base/` is
reserved for future atomic UI primitives (buttons, inputs). Path alias `@/*` → `src/*` (set
in both `vite.config.ts` and
`tsconfig.app.json`) — prefer it over relative `../../` imports.

### Config files

- `power.config.json` — app identity (`appId`, environment), build output wiring
  (`buildPath`/`buildEntryPoint`/`localAppUrl`), and `databaseReferences` (the Dataverse
  data-source map referenced above).
- `.power/schemas/dataverse/*.Schema.json` — raw per-table schema snapshots backing codegen.
